# 공급·품질 체크리스트 간소화 검토

2026-10-02. 공개 기준은 114개 component, 116개 registry item,
34개 snapshot입니다. Goal 관리용 추정은 약 89%입니다. 이번 검토는
검사 코드나 배포 절차를 변경하지 않습니다.

## 확인한 문제

현재 로드맵에는 변경 유형별 검사 8줄과 예외 설명이 이어집니다.
내용상 중복 검사를 줄였어도 새 component마다 전체 표를 점검해야
하는 것처럼 읽힙니다. 실제 `Verify UI`는 PR과 `main`에서
typecheck, UI 테스트, build, `registry:release-check`, 생성된
`docs/` diff를 실행합니다. 통과한 동일 commit의 CI 결과를 사람이
다시 검사할 이유는 없습니다.

더 큰 비용은 snapshot 절차입니다. registry 내용이 바뀔 때
`registry:release-check`가 현재 빌드와 일치하는 전체 snapshot을
요구합니다. PR #56의 마지막 후보에서도 245개 파일과 5,688줄이
변경됐습니다. provenance의 검증 문구만 바꿔도 전체 item의 고정
해시와 snapshot을 갱신해야 합니다. 이는 검사 강도의 문제가 아니라
고정 출처 정보와 변하는 검증 기록이 결합된 산출물 구조의 문제입니다.

## 적용 판단

릴리스마다 확인할 기본 항목은 다음 세 가지입니다.

- 해당 commit의 적용되는 CI가 통과했는지 확인합니다.
- 변경한 사용 흐름이 동작하는지 대표 경로 하나로 확인합니다. 정적
  표시 component는 preview가 그 증거가 될 수 있습니다. callback이나
  form 값을 추가했다면 그 흐름을 실행해야 합니다.
- 새 component의 export·registry·출처·Usage와 preview를 맞추고,
  공개했다면 변경 item URL과 배포 결과를 릴리스 묶음당 확인합니다.

추가 검사는 변경이 그 위험을 실제로 만들 때만 적용합니다. 외부
component 코드를 가져오면 같은 revision의 공식 문서·source·LICENSE·
의존성·접근성을 확인합니다. focus·pointer·browser API·핵심 반응형
배치가 새로우면 브라우저에서 검사합니다. 설치 경로가 바뀌면 별도
소비자 설치를 검사합니다. 해당하지 않는 환경은 미검증으로 적고
통과한 것으로 기록하지 않습니다.

확인된 값 손실·제출 오류·keyboard 접근 불가·필수 고지 누락·설치
실패와 적용되는 CI 실패는 수정판을 확인할 때까지 출시를 막습니다.
핵심 상호작용을 아직 실행하지 않았다면 구현은 기록하되 공급 완료로
세지 않습니다. 과거 10개 운영 과제의 완료 수는 릴리스 점수가
아닙니다. 기준을 간결하게 바꾼 것만으로 goal 진척도를 올리지
않습니다.

## 절차 개선 후보

snapshot 생성 시점을 공개 릴리스 단위로 옮기려면 PR CI의
`verify-current` 적용과 배포 작업을 함께 바꿔야 합니다. 현재는
PR마다 전체 snapshot을 만들도록 강제됩니다. provenance의 고정
출처·LICENSE와 실행 시점에 따라 바뀌는 검증 상태를 분리하는
방안도 별도 설계가 필요합니다. 둘 다 이번 검토에서 구현하거나
검증하지 않았으므로 현행 CI를 우회하지 않습니다.

이 기준은 [로드맵](component-roadmap.md#공급과-품질의-판정-단위)에
반영했습니다. 진행 중인 QueryBuilder에는 조건 편집·적용 테스트와
좁은 preview 배치 검사를 적용하고, 기존 registry 설치 방식의 개별
소비자 재설치는 기본 조건으로 두지 않습니다.
