# 공급·품질 체크리스트 현재 적용 검토

2026-10-02 현재 공개 기준은 118개 component, 120개 registry item,
39개 snapshot입니다. Goal 관리용 추정은 약 93%입니다. 이번 검토는
릴리스 상태나 검사 코드를 바꾸지 않습니다.

## 확인한 현재 상태

- 로드맵은 변경분에 해당하는 검사만 적용하도록 정했습니다. 확인된
  값 손실·제출 오류·keyboard 접근 불가·설치 실패·필수 고지 누락과
  적용되는 CI 실패는 출시를 막습니다.
- PR #70 이후 draft PR에는 현재 빌드의 새 snapshot이 필요하지
  않습니다. Ready PR과 `main`에서 `verify-current`를 실행하며,
  draft·ready·main 실행 결과를 확인했습니다.
- `Verify UI`는 문서만 바뀐 PR에도 typecheck, 전체 UI 테스트,
  build, 과거 snapshot 검사와 생성된 `docs/` diff를 실행합니다.
  변경 영향과 무관한 전체 검사 비용은 남아 있습니다.
- 로드맵에는 screen reader·touch·Safari·RTL 등을 해당 지원을
  주장하거나 관련 경로를 변경할 때 검사한다고 적은 뒤, 그 외에도
  `미검증`으로 기록한다고 적혀 있습니다. 이를 개별 릴리스마다
  열거하면 적용되지 않는 검사가 결함처럼 누적됩니다.

이후 작성한 AnchorNav 공개 후보 PR #72는 새 component 1개와
현재 snapshot 1개를 위해 생성 파일을 포함한 298개 파일,
6,715줄 추가·187줄 삭제가 포함됐습니다. 공개 후보의 불변
snapshot 요구는 유지하되, 그 비용을 개별 component 품질
검사의 강도와 혼동하지 않아야 합니다.

## 적용 판단

개별 변경의 공급 판정은 해당 commit의 CI, 변경한 핵심 사용 흐름의
실행 증거, 공개할 때의 manifest·변경 item URL과 배포 상태로
충분합니다. 새 component는 독립 사용처, export·registry·출처,
동작하는 preview와 Usage를 갖춥니다. 외부 코드 도입, 새 focus·
pointer·browser API, 핵심 반응형 배치, 설치 경로 변경은 해당 위험이
있을 때만 추가 검사합니다. 이미 통과한 동일 commit의 CI를 수동으로
반복하지 않고 표준 registry item마다 별도 소비자를 만들지 않습니다.

검사 상태는 `통과`, `해당 없음`, `미검증`, `차단`으로 구분합니다.
`미검증`은 적용되는 검사를 실행하지 못했거나 명시적으로 지원을
평가하는 환경에만 씁니다. 해당하지 않는 환경을 릴리스마다
나열하지 않습니다. 핵심 상호작용을 어느 방식으로도 실행하지
못했으면 공급 완료로 세지 않습니다.

## 남은 절차 비용

문서만 바뀐 PR의 전체 코드 검사를 줄이려면 workflow의 변경 경로
판별과 필수 status check를 함께 설계해야 합니다. 과거 snapshot의
전수 검사를 공개 후보 단계로 옮기는 경우에도 기존 snapshot의
손상을 병합 전에 잡는 검사는 유지해야 합니다. provenance의 고정
출처·LICENSE와 시점별 검증 기록을 분리하면 문구 수정으로 전체
snapshot을 갱신하는 비용을 줄일 수 있습니다. 셋 모두 이번
검토에서 구현·검증하지 않았습니다.

체크리스트의 항목 수를 goal 완료율로 환산하지 않습니다. 이번
검토만으로 공급 수량과 goal 관리용 추정 약 93%는 바뀌지 않습니다.
