# 공급·품질 체크리스트 수준 재검토

2026-10-02 검토 당시 공개 기준은 116개 component, 118개
registry item, 37개 snapshot이었습니다. Goal 관리용 추정은 약
91%였고 `ModelSelector`는 로컬 초안이어서 공개 수량에 포함하지
않았습니다. 후속 공개 결과는
[편입 기록](model-selector-2026-10-02.md)을 참고하세요.

## 판단

현재 품질 하한 자체가 과도하다고 보기는 어렵습니다. 사용자가 값을
고르거나 제출하는 component라면 실제 선택·제출 흐름을 한 번 실행해야
`ready-made`라고 할 수 있습니다. 확인된 값 손실, 제출 오류,
keyboard 접근 불가, 설치 실패, 필수 LICENSE 고지는 출시 차단으로
유지합니다.

다만 절차는 경직되어 있습니다. 로드맵은 변경 위험별 기준을 이미
정했지만 하단 여섯 단계에서 이를 다시 열거합니다. 같은 검사를 두
번 요구하는 것처럼 읽힙니다. `Verify UI`는 모든 PR에서 전체
typecheck·UI 테스트·build·`registry:release-check`를 실행하고,
registry가 바뀌면 `verify-current` 때문에 전체 item의 새 snapshot을
PR에 포함해야 합니다. provenance의 검증 문구만 바뀌어도 소비자
고지의 hash와 전체 snapshot이 연쇄 변경됩니다. 이 비용은 개별
component의 위험과 비례하지 않습니다.

이번 `ModelSelector` 공개 후보에서도 새 component 1개를 위한
snapshot과 문서 산출물로 277개 파일, 5,895줄이 변경됐습니다.
`registry:release-check`는 통과했지만 PR diff의 크기는 기능 변경의
검토 범위보다 훨씬 큽니다.

현재 판정은 아래 세 가지만 기본으로 읽는 것이 적절합니다.

- 변경한 핵심 사용 흐름을 자동 테스트 또는 브라우저 중 적합한
  방식으로 실행합니다. 정적 표시 변경은 preview로 확인할 수 있습니다.
- 새 component는 독립 사용처, export·registry·출처, 실제 preview와
  Usage를 갖춥니다. 공개 릴리스는 변경 item URL과 배포 상태를
  묶음당 한 번 확인합니다.
- 공개 후보 commit의 적용되는 CI 결과를 확인하고 같은 결과를
  수동으로 반복하지 않습니다.

외부 코드를 도입하거나 focus·pointer·browser API·핵심 반응형
배치·설치 경로를 바꾼 경우에만 해당 검사를 추가합니다. 기존
component에서 그대로 물려받은 동작은 다시 시험하지 않습니다.
`통과`·`해당 없음`·`미검증`·`차단`을 구분하고, 적용되지 않는
screen reader·touch·Safari·RTL 검사를 매 릴리스의 남은 결함처럼
열거하지 않습니다. 지원 범위를 새로 주장할 때는 해당 환경을
검사합니다.

## 절차 개선 우선순위

로드맵의 여섯 단계 중 앞의 적용 기준과 겹치는 설명을 한 곳으로
합치는 문서 정리가 먼저입니다. 이후 PR 초안의 정합성 검사와
공개 후보의 불변 snapshot 검사를 분리할 수 있습니다. 이때 병합
전 snapshot 생성·검사를 보장해야 하므로 CI 명령 하나만 제거해서는
안 됩니다. provenance의 고정 출처·LICENSE와 시점별 검증 결과를
분리하면 문구 수정만으로 전체 snapshot을 갱신하는 일을 줄일 수
있습니다. 이 두 도구 변경은 별도 구현·검증 범위입니다.

이번 검토는 기준 해석이며 CI·출시 판정·제품 동작을 변경하지
않았습니다. 새 component 공급이나 공개 검증이 없으므로 goal
관리용 추정은 약 91%로 유지합니다. 코드·브라우저·배포 검사는
이번 검토를 위해 새로 실행하지 않았습니다.
