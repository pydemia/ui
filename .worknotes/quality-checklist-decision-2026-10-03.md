# 공급·품질 체크리스트 적용 수준 재검토

## 2026-10-03 추가 재검토: 사람 검토의 기본 범위 축소

현행 문구는 변경분 중심이지만 실제 작업에서는 독립 component마다
390px·1280px, light·dark, 로컬·공개 브라우저 확인을 반복했습니다.
`TreemapChart`의 값 계산·빈 상태는 대상 테스트로, 계층 배치는 로컬
preview로 확인했습니다. 공개 URL의 응답은 릴리스 공급 확인이며
계산이나 배치를 다시 검증하는 절차가 아닙니다. 이 모든 증거를 매번
같은 조합으로 요구할 근거는 없습니다.

앞으로 사람 검토의 기본 질문은 두 가지입니다. 바뀐 핵심 동작을
관련 테스트 **또는** 실제 preview·브라우저 실행으로 확인했는가,
사용자가 복사할 API·Usage가 공급물과 일치하는가. 자동화가 이미
확인하는 export·registry·provenance·snapshot 파일 전체를 사람이 다시
대조하지 않습니다. 독립적인 정적 표시 변경은 영향을 받는 상태의
preview 한 번으로 충분합니다. 폭·theme·focus·pointer·form·browser
API는 실제 변경이 닿는 경로만 추가로 확인합니다. 실제 screen reader,
touch, Safari, RTL 전수 검사는 해당 지원을 약속하거나 관련 동작을
바꿨을 때만 범위에 넣습니다.

새 component에는 독립 사용처, export·registry·출처 metadata, 동작하는
preview와 Usage를 갖춰야 합니다. 외부 코드를 편입할 때의 revision·
LICENSE·의존성·접근성 확인과, 확인된 값 손실·제출 오류·keyboard
접근 불가·필수 고지 누락·설치 실패는 계속 출시 차단입니다. 원본
구현에서 디자인 개념만 참고했다면 외부 코드의 LICENSE 검사를
반복하지 않습니다. 새 설치 형식·target·의존 경로가 없으면 별도
소비자 설치도 반복하지 않습니다.

CI와 현재 snapshot은 개별 component의 점수가 아니라 **릴리스 묶음의
조건**입니다. PR과 `main`의 자동 검사는 각각 실행되지만 사람이 같은
동작을 두 번 검토하지 않습니다. 배포 뒤에는 manifest와 바뀐 대표
item의 공개 접근을 확인합니다. 공개 사이트에서 로컬 상호작용을
재실행하는 검사는 배포 환경에서만 생기는 위험이 있을 때 추가합니다.
작업 기록은 한 곳에 실제 실행 결과와 적용됐지만 미실행한 검사만
남기고, 진척도·인계 기록에서는 링크합니다. 이 조정은 사람 검토의
적용 범위만 바꿉니다. 현재 `verify.yml`의 PR·`main` 전체 검사와
review 준비 PR의 snapshot 요구, snapshot 전체 복제는 그대로입니다.
별도 자동화 개선 없이는 그 실행 비용이 줄었다고 말할 수 없습니다.
Goal 관리용 추정은 약 98%로 유지합니다.

## 2026-10-03 재판정: 품질 문턱과 릴리스 절차

현행 기준의 필수 수동 검사는 변경한 핵심 동작 한 번과 공급물의
일치 확인입니다. 이 정도는 ready-made component의 최소 수준입니다.
다만 로드맵이 구현 검토와 공개 절차를 긴 문장으로 이어 적어,
개발 중에도 모든 검사를 끝내야 한다는 인상을 줬습니다. 로드맵을
세 단계의 최소 증거와 변경 위험별 검사로 줄였습니다.

실제 부담은 품질 판단보다 릴리스 자동화에 있습니다.
`.github/workflows/verify.yml`은 제품 코드가 바뀌면 전체
typecheck·테스트·build·registry 검사를 실행하고, 검토 준비 PR과
`main`에서는 현재 snapshot도 요구합니다. `registry-release.mjs`
`create`는 변경 item만이 아니라 전체 item을 새 ID 아래 저장합니다.
`HistogramChart` 릴리스의 322개 변경 파일 중 280개가 이 복제였습니다.
이는 component마다 더 많은 검사를 요구할 이유가 아닙니다. 한 번의
릴리스에 여러 변경을 담을 수 있고, 같은 commit의 CI·브라우저
증거를 다시 만들지 않습니다.

공개 준비의 차단 사유는 확인된 값 손실·제출 오류·interactive 요소의
keyboard 접근 불가·필수 고지 누락·설치 실패·적용 CI 실패입니다.
실행하지 않은 핵심 동작은 `공개 준비`로 판정하지 않습니다. CI 자체가
실행되지 않았거나 Vercel 배포가 제한된 경우는 제품 결함과 구분해
`공개 대기`로 기록합니다. screen reader·touch·Safari·RTL 등의
포괄적인 수동 검사는 지원 범위로 명시하거나 관련 경로를 변경했을
때 적용합니다. 이번 재판정으로 검사 코드·workflow·snapshot 형식은
바꾸지 않았고, 공개 수량과 Goal 관리용 추정 약 98%도 올리지 않습니다.

후속 실적용 결과는 [HistogramChart 작업 기록](histogram-chart-2026-10-03.md)에
남겼습니다. 원본 component 하나의 공개 검사에는 변경분 중심 기준을
적용했고, 릴리스의 322개 변경 파일 중 280개가 snapshot 전체 복제였습니다.
검사 하한을 더 낮출 근거보다 생성·저장 비용을 줄일 근거가 큽니다.

2026-10-03. 현행 [로드맵](component-roadmap.md#공급과-품질의-판정-단위)은
변경분만 검사하고, 같은 동작과 CI 결과를 반복하지 않도록 정해 두었습니다.
기본 품질 하한은 낮출 필요가 없습니다. 경직성은 그 하한을 개발 중인
후보와 공개 릴리스에 한꺼번에 적용하거나, 자동 생성량과 배포 대기를
component 품질 미달처럼 기록하는 데 있습니다.

이번부터 판정은 다음 세 상태로 기록합니다.

| 상태 | 필요한 증거 |
| --- | --- |
| 구현 검토 | 실제 사용처·기존 API와의 차이, 변경한 동작의 관련 테스트 또는 preview |
| 공개 준비 | export·registry·출처·Usage·preview의 일치, 공개 후보의 적용 CI, 변경한 핵심 동작의 실행 |
| 공개 확인 | 배포 성공, manifest와 변경한 공급 경로의 대표 URL 접근 |

정적 표시에는 실제 preview와 값·경계의 관련 테스트를 사용합니다.
새 focus·pointer·browser API·반응형 동작에는 그 경로를 검증하는
테스트나 브라우저 실행을 추가합니다. 새 설치 형식·target·의존
경로가 없으면 별도 소비자 설치를 반복하지 않습니다. 직접 작성한
component에 일반 개념만 참고했다면 외부 코드의 revision·LICENSE
조사를 요구하지 않습니다. 외부 코드를 편입했을 때는 기존 출처
기준을 그대로 적용합니다.

공개 준비 상태에서 확인된 값 손실·제출 오류·keyboard 접근 불가·
필수 고지 누락·설치 실패·적용 CI 실패는 차단합니다. 핵심 동작의
실행 증거가 없으면 공개 준비로 판정하지 않습니다. Vercel 제한으로
배포되지 않은 후보는 품질 실패가 아니라 공개 대기입니다. 이때
공개 확인을 마친 수량에는 포함하지 않습니다.

사람이 검토할 기록은 작업별 `.worknotes` 하나에 적용한 증거와
확인된 결함, 실제로 적용되지만 실행하지 못한 검사만 남깁니다.
과거 10개 운영 과제의 완료 개수는 릴리스 점수로 사용하지 않습니다.
같은 내용의 검사 결과를 로드맵·진척도·인계 문서에 복제하지 않고,
그 문서에서는 작업 기록으로 연결합니다.

`main`의 비렌더링 문서 변경에 대한 전체 UI 검사 생략은 PR #115와
병합 후 CI에서 확인했습니다. 따라서 이를 남은 고정 비용으로
계속 적지 않습니다. 현재 남은 큰 비용은 provenance 전체 hash가
무관한 item 고지에 전파되고, snapshot 생성기가 매번 전체 item을
`registry/releases/`와 `docs/r/releases/`에 복제하는 구조입니다.
이는 별도 생성·저장 방식 개선 과제이며 이번 component의 품질
체크박스가 아닙니다. 기존 불변 URL·의존 경로·고지 전달을 보존하며
변경해야 합니다.

당시 작업 중이던 `BoxPlotChart`에는 원본 코드의 수치 경계 테스트,
표의 정확한 값, preview와 좁은 화면 배치, 적용 CI를 확인합니다.
외부 코드 편입이나 새 설치 방식의 검사는 적용하지 않습니다.
이번 재검토는 기준 문서와 작업 판정만 바꾸며, 공개 공급이나 goal
관리용 추정 약 98%를 올리지 않습니다.
