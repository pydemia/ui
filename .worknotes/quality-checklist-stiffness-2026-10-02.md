# 공급·품질 체크리스트의 경직성 재검토

## 2026-10-02 절차 변경 후보

`Verify UI`의 PR 경로를 변경해 비렌더링 Markdown 기록만 바뀐 PR은
diff 공백 검사로 끝내는 초안을 작성했습니다. `apps/docs/`와 생성된
`docs/`를 포함한 제품·설치 경로 변경, `main` push는 전체 검사를
유지합니다. 실제 CI 결과 확인 전에는 절차 비용이 줄었다고 판정하지
않습니다. [작업 기록](ci-scope-2026-10-02.md)에 범위를 남겼습니다.

## 2026-10-02 추가 판단

판정 문구보다 자동화의 고정 실행량이 더 큰 부담입니다. 새
`NotificationCenter`의 릴리스에는 public export·registry·출처·
preview·Usage, 변경한 읽음/필터 동작 한 차례와 같은 commit의 CI를
적용합니다. 원본 구현이므로 새 upstream의 source·LICENSE 대조는
적용되지 않습니다. 동일 동작을 로컬과 공개 사이트에서 반복 실행하지
않고, 공개 manifest와 변경 item URL은 릴리스당 확인합니다.

운영 기준은 세 단계가 적당합니다. 문서 변경은 변경 링크·예시와
docs build, 기존 component의 표시·동작 변경은 영향받은 상태와
회귀 검사, 새 component·설치 경로 변경은 공급 경로와 핵심 사용
흐름을 확인합니다. 확인된 값 손실·제출 오류·keyboard 접근 불가·
설치 실패·필수 고지 누락은 어느 단계에서도 출시를 막습니다.
`verify.yml`과 snapshot 형식은 아직 바뀌지 않았으므로 실행 시간이
줄었다고 기록하지 않습니다. CI의 문서 전용 분기와 snapshot 중복
저장은 별도 구현·검증 대상입니다. 이 재검토만으로 goal 관리용
추정 약 97%를 올리지 않습니다.
실제로 `NotificationCenter`의 51번째 snapshot과 고지 갱신은
291개 파일을 변경합니다. 검사 수준보다 snapshot 전체 복제 방식이
한 component 릴리스의 diff를 크게 만드는 직접 원인입니다.

2026-10-02. 공개 기준은 125개 component, 127개 registry item,
48개 snapshot입니다. Goal 관리용 추정은 약 97%입니다. 이번 검토는
제품 코드나 CI 설정을 바꾸지 않았으며 출시 검사를 실행하지 않았습니다.

## 확인한 상태

현재 [로드맵](component-roadmap.md#공급과-품질의-판정-단위)과
[적용 기준](quality-checklist-current-review-2026-10-02.md)은 이미
변경분 중심입니다. 같은 commit의 CI를 재사용하고 핵심 흐름은 자동
테스트 또는 브라우저 중 하나로 확인합니다. 정적 표시는 preview로
확인할 수 있고, 표준 item의 별도 소비자 설치를 반복하지 않습니다.
새 component의 export·registry·출처·Usage·preview는 공급물의
기본 구성으로 유지하는 편이 맞습니다.

경직성은 주로 실제 실행 절차에 남았습니다.

- `.github/workflows/verify.yml`은 문서 전용 PR에도 전체 UI 테스트,
  build, registry 검사를 실행합니다. draft PR의 현재 snapshot 검사는
  생략하지만 나머지 작업은 같습니다. `main`에서도 전체 검사를
  반복합니다.
- 새 snapshot은 내용이 바뀐 item만 저장하지 않고 전체 item을
  `registry/releases/`와 `docs/r/releases/`에 복제합니다. component
  하나를 자주 공개할수록 검토 diff와 저장량이 커집니다.
- 2026-09-29의 라이브러리 전체 조사 항목과 과거 작업 기록에는
  보조기술·touch·Safari·RTL 등의 미검증 상태가 누적돼 있습니다.
  현행 기준에서는 매 릴리스의 차단 항목이 아니지만 기록을 함께
  읽으면 공급 자체가 미완료인 듯 보입니다.

## 적용할 판정

릴리스의 사람 검토는 다음 질문으로 마칩니다.

1. 바뀐 사용처와 공개 API·Usage·preview가 서로 맞습니까?
2. 바뀐 핵심 동작의 실행 증거가 있습니까? 정적 변경은 변경한
   preview 확인으로 충분합니다.
3. 적용되는 자동 검사가 통과했고 공개한 경로가 열립니까?

`verify-current`는 snapshot의 전체 파일 목록·hash·dependency와
배포용 복사본의 일치를 검사합니다. 설치·배포 경로가 그대로라면
공개 사이트에서는 manifest와 변경 item 중 대표 URL 하나를 표본으로
확인해도 됩니다. 변경 item의 모든 URL을 사람이 각각 열 필요는
없습니다. 경로 구조가 바뀌었다면 영향을 받은 URL과 소비자 설치를
별도로 확인합니다.

같은 증거를 로컬·PR·공개 사이트에서 반복하지 않습니다. 새 외부
코드를 실제로 도입했을 때만 해당 revision의 공식 문서·소스·LICENSE·
의존성·접근성과 고지를 확인합니다. 새 focus·pointer·browser API·
핵심 반응형 동작이나 설치 경로에는 그 변경을 다루는 검사를 추가합니다.
기존 component의 조합·표시 변경에는 신규 component 조사 전체를
재적용하지 않습니다.

출시를 막는 것은 적용되는 CI 실패, 확인된 값 손실·제출 오류·keyboard
접근 불가, 필수 고지·설치·공개 경로 실패, 새 핵심 상호작용의 실행
증거 부재입니다. 선택한 모든 환경을 매번 검증할 필요는 없습니다.
지원한다고 명시한 환경이나 변경한 경로는 검증하고, 그 외 표본 조사는
라이브러리 전체의 별도 작업으로 둡니다. `미검증`은 적용되지만
실행하지 못한 검사에만 사용하며, `해당 없음`과 구분합니다.

## 절차를 줄일 다음 변경

문서 전용 PR에는 문서 build와 변경한 링크·Usage·preview 검사를
적용하고, UI·registry 전체 검사는 해당 파일이 바뀐 PR에서 실행하도록
workflow를 분기합니다. 공개 후보와 `main`의 전체 검사 및 현재
snapshot 확인은 유지합니다. snapshot 형식을 바꿀 때는 기존 불변 URL,
dependency 참조와 rollback 동작을 먼저 확인해야 합니다. 이 두 변경은
이번 검토에서 구현하거나 통과로 판정하지 않았습니다.

체크리스트 문구를 더 늘리거나 10개 누적 조사 항목의 완료 개수로
goal을 계산하지 않습니다. 기준을 간결하게 해석한 것만으로 goal
진척도는 올리지 않습니다.
