# 공급·품질 체크리스트 재검토

## 2026-10-03 현재 적용: 검사 수준과 릴리스 비용 분리

사용자 지적은 타당합니다. 필수 증거 세 가지(API·사용 코드·공급물의
일치, 변경한 핵심 동작의 실행, 적용 CI)는 유지하지만, 이를 모든
상태·환경에 대한 수동 검사 목록으로 확장하지 않습니다. 정적 차트는
정확한 값의 텍스트·표, 경계값 테스트, 실제 preview 한 번이면
기본 판정을 마칩니다. 클릭·제출·focus 같은 새 동작이 없으면 그
흐름의 브라우저 검사도 요구하지 않습니다. 일반적인 차트 개념만
참고해 직접 구현한 경우에는 참고 제품의 source·LICENSE 대조를
외부 코드 도입 검사로 취급하지 않습니다.

현재 `verify.yml`은 draft PR에서 `verify-current`를 건너뛰고,
review 준비 PR에서 현재 snapshot을 검사합니다. `main` push는
문서만 바뀌어도 전체 검사를 다시 실행합니다. `registry-release.mjs`
`create`는 item 하나가 바뀌어도 모든 item을 새 ID 아래 복제합니다.
이 고정 비용을 component 품질 점수로 계산하지 않습니다. 가능한
변경을 한 릴리스 묶음에 담고 snapshot·공개 URL은 묶음당 확인합니다.
값 손실·제출 오류·keyboard 접근 불가·필수 고지 누락·설치 실패·
적용 CI 실패는 계속 출시 차단입니다. 배포 지연은 `공개 대기`로
기록합니다. 이번 판정은 CI·snapshot 형식의 변경이 아니며,
공개 133개 component·135개 item과 Goal 추정 약 98%는 그대로입니다.

## 2026-10-03 추가 판단: 작은 변경의 고정 비용

이전 판단은 검사 항목이 이미 변경분 중심이라는 이유로 현행 하한을
유지했습니다. 실제 `LogViewer`의 선택형 자동 스크롤 작업에서는
그 설명만으로 부족했습니다. 원본 component의 의존성·접근성
metadata를 갱신하자 공통 MIT 고지에 적힌 `provenance.json` 전체
SHA-256과 달라져 `registry:check`가 실패했습니다. 토글을 기존
native 버튼 패턴으로 구현해 새 의존성과 metadata 변경을 없애자
같은 검사가 통과했습니다. 작은 동작 변경이 라이선스 원문의 변경
없이 모든 item의 고지와 snapshot을 다시 생성하게 하는 결합입니다.

현행 CI는 비렌더링 문서 전용 PR을 제외한 PR과 `main`에서 전체
typecheck·테스트·build·registry 검사를 각각 실행합니다. 검토 준비
PR과 `main`은 현재 snapshot도 요구합니다. 62번째 snapshot은
`pyd-log-viewer`의 소스만 바뀌었어도 135개 item을 원본과 배포용
두 위치에 저장했습니다. 검사를 더 많이 수행한 만큼 사용 가치가
높아졌다고 해석하지 않습니다.

이후 작업의 사람 검토는 변경한 API·사용 코드의 일치, 핵심 동작
한 번의 실행, 적용 CI 결과 세 가지로 끝냅니다. 새 component에는
독립 사용처·registry·출처·preview·Usage를 추가로 확인합니다.
외부 코드, 설치 경로, focus·browser API 등은 실제로 바뀐 경로만
검사합니다. 같은 commit의 CI와 이미 실행한 브라우저 흐름은
반복하지 않습니다. snapshot과 공개 URL은 릴리스 묶음당 한 번
확인하고, Vercel 제한으로 배포되지 않은 변경은 품질 실패 대신
`공개 대기`로 표시합니다. 값 손실·제출 오류·keyboard 접근 불가·
필수 고지 누락·설치 실패·적용 CI 실패는 그대로 출시 차단입니다.

metadata와 라이선스 고지의 결합, 전체 item snapshot 복제,
검토 준비 PR·`main`의 중복 CI는 자동화 개선 대상으로 남깁니다.
이 문서만으로 workflow나 snapshot 형식이 바뀐 것은 아닙니다.
과거 10개 조사 항목의 완료 수와 Vercel 배포 지연을 component
품질 점수로 사용하지 않습니다. 검토 시점의 Goal 관리용 추정은
약 97%였고 PR #108의 production 공개 확인 뒤 약 98%로
조정했습니다. 공개 근거는
[LogViewer 작업 기록](log-viewer-follow-tail-2026-10-03.md)에 있습니다.

2026-10-03 후속 판정: 이전 표는 `구현 후보`에도 export·registry·
preview·Usage를 모두 요구해, 작업 중인 component와 공개 가능한
공급물을 같은 기준으로 읽히게 했습니다. 개발 중에는 실제 사용처와
중복 여부를 판단하고 영향받은 동작만 확인합니다. 공개 후보로 옮길
때 공급물의 정합성과 CI·snapshot을 확인합니다. 이번에는 제품 코드나
CI를 변경하지 않았습니다.

작업 기록도 경직돼 있었습니다. 같은 검사 결과를 로드맵·진척도·
인계·검증 문서에 반복해서 옮기지 않습니다. 작업별 근거는 관련
`.worknotes` 기록 한 곳에 적고, `NEXT_SESSION.md`에는 상태와 링크를
남깁니다. 기존 `research/verification.md`는 장기 보존이 필요한 제품
검증 내용이 바뀔 때만 갱신합니다. 적용되지 않는 환경 검사를 릴리스의
미검증 목록에 반복하지 않습니다.

이 구분은 개발 중 후보를 공개된 component로 세거나 확인된 값 손실·
제출 오류·keyboard 접근 불가·필수 고지 누락·설치 실패·적용 CI 실패를
허용한다는 뜻이 아닙니다. PR #106의 병합 commit은 Verify UI가
통과했고 마지막 PR commit의 Vercel preview는 READY입니다.
production은 이전 배포를 가리킵니다. 공개 공급 상태와 goal 관리용
추정 약 97%는 그대로입니다.
[병합·공개 상태](release-pr106-2026-10-03.md)에 근거를 남겼습니다.
이 문서 변경은 PR #106의 최신 commit에 포함됐고 Verify UI run

2026-10-03. 현행 기준은 변경분의 핵심 동작을 자동 테스트 **또는**
브라우저에서 확인하고, 기존 설치 경로의 새 item마다 별도 소비자 설치를
요구하지 않습니다. component별 PR·snapshot도 요구하지 않습니다.
따라서 검사 항목을 일괄 삭제할 근거는 없습니다. 문제는 구현 검증,
공개 가능 여부, 라이브러리 전체의 장기 과제가 같은 완료율처럼 읽히는
점과 반복 생성·배포 비용입니다.

## 이번 판정

| 상태 | 필요한 증거 | 완료 표기 |
| --- | --- | --- |
| 개발 중 후보 | 사용처와 중복 판정, 영향받은 핵심 동작의 테스트 또는 브라우저 실행 | 구현·로컬 검증 완료 |
| 공개 후보 | API·export·registry·preview·Usage·출처 일치, 같은 commit의 적용 CI, 릴리스 묶음의 snapshot 및 현재 내용 일치 | 공개 준비 완료 |
| 공개 공급 | production 배포, manifest와 바뀐 의존 경로의 대표 item URL 접근 | 공개 완료 |

외부 코드 또는 구체적인 디자인·API를 편입하면 공식 문서, 해당
revision의 source·LICENSE, 의존성과 접근성 검토를 유지합니다. 기존
조사를 같은 revision에서 재사용할 수 있습니다. 원본 구현에 참고한
일반적인 접근성 명세를 외부 component 코드 도입으로 취급하지 않습니다.
값 손실, 잘못된 form 제출, keyboard 접근 불가, 필수 고지 누락, 적용 CI
실패와 설치 실패는 확인되면 공개를 막습니다.

새 focus·pointer·browser API·핵심 반응형 배치, 설치 형식·target·의존
경로, 색상·배치가 바뀔 때는 현행 로드맵의 영향 범위만 추가로 검사합니다.
실제 screen reader·touch·Safari·RTL 전수 검사와 모든 item의 개별
설치는 릴리스별 기본 체크박스에 넣지 않습니다. 해당 환경을 지원한다고
명시하거나 새 상호작용이 그 환경에 의존하면 대상 검사를 적용합니다.
실행하지 않은 적용 검사는 `미검증`, 적용되지 않는 검사는 `해당 없음`으로
구분합니다. `해당 없음`을 미완료 건수에 더하지 않습니다.

`BarList`는 PR·`main` CI와 Pages가 통과했지만 Vercel 배포 제한으로
공개 item이 404입니다. 이는 **품질 실패가 아니라 공개 대기**이며,
공개 공급 완료로도 세지 않습니다. `BulletChart`와 `FunnelChart`는
[PR #106](https://github.com/pydemia/ui/pull/106)의 같은 60번째
snapshot에 묶였고 검토 준비 Verify UI를 통과한 공개 후보입니다.
production JSON은 404이므로 공개 공급 완료로 세지 않습니다.
구현 검증, 공개 준비, 공개 공급을 하나의 체크리스트 점수로
합치지 않습니다.

## 실제 경직성이 있는 곳

- `Verify UI`는 코드 PR과 `main` push에서 전체 typecheck·테스트·build·
  registry 검사를 반복합니다. `main`의 비렌더링 문서 변경에도 전체
  검사가 적용됩니다. 변경 영향에 따른 CI 범위 조정은 별도 workflow
  변경과 실패 위험 검토가 필요합니다.
- 새 snapshot은 현재 item 전체를 `registry/releases/`와
  `docs/r/releases/`에 다시 저장합니다. 공통 출처 고지의 hash 변경도
  관련 없는 현재 JSON 다수를 갱신합니다. 이 파일 수는 component의
  품질이나 사용 가치를 측정하지 않습니다.
- Vercel 배포 횟수 제한은 코드 품질 판정과 독립적입니다. 제한을
  피하려고 공개 경로 검증을 생략하거나 공개 완료로 표시하지 않습니다.

따라서 현재의 **변경분 중심 품질 하한은 유지**하고, 진행 상태는 위
세 단계로 보고합니다. CI 중복, snapshot 저장 방식, 공통 고지 결합은
검증 기준을 낮추는 대신 별도 구현 과제로 다룹니다. 이번 재검토는
기준의 해석과 기록 방식을 정리한 것이며 제품 코드·CI·공개 수량을
바꾸지 않았습니다. Goal 관리용 추정은 약 97%로 유지합니다. 이 수치는
체크박스 완료율이 아니라 사용 사례 범위와 공개 상태를 함께 보는
추정치입니다.
