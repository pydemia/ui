# 공급·품질 체크리스트 실무 기준 재검토

2026-10-02 현재 공개 기준은 119개 component, 121개 registry item,
40개 불변 snapshot입니다. TreeNav는 로컬 초안이므로 포함하지 않습니다.
Goal 관리용 추정은 약 94%입니다.

## 확인한 부담

- 로드맵의 현재 기준은 변경한 핵심 흐름을 테스트 **또는** 브라우저로
  확인하도록 합니다. 과거 검토 문서의 테스트 **및** 브라우저 요구와
  다르게 읽힐 수 있으므로 현재 로드맵을 적용 기준으로 삼습니다.
- `Verify UI`는 모든 PR과 `main` push에서 typecheck, 전체 UI 테스트,
  build, 과거 snapshot 전수 검사와 생성된 `docs/` diff를 실행합니다.
  Ready PR과 `main`은 현재 snapshot도 검사합니다. CI의 실행 비용과
  사람이 매 component마다 반복해야 하는 판정 항목을 구분해야 합니다.
- 기존 snapshot 형식은 릴리스 시 전체 registry item을 복제합니다.
  AnchorNav 한 개의 공개 후보 PR #72에는 생성 파일을 포함해
  298개 파일이 변경됐습니다. component 하나마다 출시하면 이 비용을
  매번 지불합니다.
- 이전 기록에는 현재 변경에 영향받지 않는 screen reader, touch,
  Safari, RTL, rollback 검사를 매번 `미검증`으로 열거했습니다.
  현재 로드맵은 관련 기능이나 지원 주장이 없으면 해당 없음으로
  처리합니다.

## 적용 판단

새 component의 필수 근거는 독립 사용처, 공개 export·registry·출처,
동작하는 preview·Usage, 변경한 핵심 흐름의 실행 증거, 같은 commit의
적용되는 CI 결과입니다. 외부 코드 도입, 새 focus·pointer·browser API,
핵심 반응형 배치, 설치 경로 변경에는 영향받은 검사만 추가합니다.
확인된 값 손실·제출 오류·keyboard 접근 불가·설치 실패·필수 고지 누락과
적용되는 CI 실패는 출시 차단으로 유지합니다. 외부 upstream의 동일
revision 문서·소스·LICENSE·의존성·접근성 확인도 해당 코드나 설계를
편입할 때 유지하고, 이미 조사한 동일 revision의 기록은 재사용합니다.

공개 작업은 component마다 별도 PR·snapshot을 요구하지 않습니다.
서로 독립적인 구현도 검토 가능한 범위에서 한 릴리스로 묶을 수
있습니다. 이 경우 snapshot과 공개 manifest·변경 item URL은 릴리스
묶음당 한 번 확인합니다. 묶음 크기를 채우기 위해 완성된 component의
공개를 지연하거나 후보를 억지로 추가하지는 않습니다.

기록은 적용한 검사, 통과 여부, 적용되지만 실행하지 못한 검사,
확인된 결함을 구분합니다. 적용되지 않는 환경을 개별 릴리스의
결함 목록에 반복하지 않습니다. `미검증`을 `통과`로 바꾸지는 않습니다.
테스트와 브라우저를 모두 요구하는 과거 문구가 있더라도 현재 변경의
위험에 따라 필요한 증거를 선택합니다.

이번 재검토는 판정 방식과 릴리스 묶음의 운영 원칙을 명확히 한
것입니다. CI·snapshot 형식·제품 코드는 바꾸지 않았으며 새 공개
공급도 없으므로 goal 관리용 추정 약 94%를 유지합니다.
