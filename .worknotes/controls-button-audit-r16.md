# R16 Controls: transparent embedded-control presentation audit

- Date: 2026-10-16. Source-only, read-only audit of all 53 IDs in `.worknotes/browser-evidence/geometry-r14/inventory.json` whose family is Actions, Inputs, Selection, Date & time, or Overlays.
- Reviewed component TSX hooks/variants and nested controls, docs catalog callers, and the current cascade in `packages/ui/src/design-modes.css`. Prior R15 state/variant inventory is evidence context, not a substitute for this presentation pass.
- No product files, tests, browser state, build, or Git state were changed. This note is the only write.
- Goal interpretation: a control embedded in a toolbar, field, disclosure, calendar, menu, or editor should not look like a second independent pill when its parent already carries the surface. A true standalone action/field and meaningful selected/checked state can retain their mode paint. Existing Basic, approved 21 theme definitions, and PRISM design contracts must remain unchanged.

## Finding and selector priorities

**P1 — broad pressed-button paint can reintroduce a standalone shadow.** `design-modes.css:372-388` gives non-ghost `data-ui=button` action decoration, then the unconditional `button[aria-pressed]` rules at 387-388 reset shadow and paint the pressed shadow. This broad rule is independent of the Button variant. Later non-Basic exception `:where([data-ui="button"][data-variant="ghost"][aria-pressed]) { box-shadow:none }` at 967 fixes the library ghost button only inside a non-Basic design scope; it does not cover Basic, raw `<button aria-pressed>`, or non-button component hooks. The selected paint for Toggle/ToggleGroup/SegmentedControl is separately and intentionally applied at 1120-1123. Candidate: remove/narrow the generic pressed-button paint to explicit action variants; route actual selected controls through their component/state selectors. Ensure ghost's base/pressed states remain transparent while hover/focus/disabled feedback remains.

**P1 — embedded native select gets standalone field chrome.** `native-select.tsx` emits `data-ui="native-select"` and a ChevronDown suffix; theme rules at `design-modes.css:394-405, 937-960` add the full field border, fill, shadow, radius, and height. `block-editor.tsx:289-306` directly renders `<select data-ui="native-select" data-appearance="outline">` inside `[data-slot="block-toolbar"]`, adding another `border bg-surface rounded-sm` via classes 297-300. It bypasses the NativeSelect wrapper/icon but still receives the generic theme field treatment. This is the concrete representative: it is an editor type selector inside an already framed block toolbar and currently reads as an independent field/pill. Candidate: add a block-toolbar context rule that clears border, background/image, shadow and field min-height/height, keeps compact inline padding and leaves `:focus-visible` ring, disabled state and native select keyboard semantics intact. Leave standalone NativeSelect field styling unchanged.

**P1 — inline outline actions need a context hook.** `button.tsx:5-39` makes `outline` a bordered `bg-surface` button; theme decoration applies to all non-ghost buttons (`design-modes.css:372-380,386`). In `block-editor.tsx:307-324,350-353`, several move/add/delete actions sit next to the type selector within a toolbar, and three use `outline`; each is an independent rounded action surface on the block's own well. Candidate: mark toolbar-only secondary actions with a `data-slot` (or context selector) and give them transparent/no-border/no-shadow chrome under non-Basic modes, while preserving their full hit target, text/icon, focus ring, disabled opacity and danger foreground for delete. Keep `primary` actions and standalone outline examples as authored.

**P2 — date navigation arrows are individually painted controls.** The shared calendar recipe at `design-modes.css:804-806` assigns 32px squares, title fill, schedule-cell shadow and heading ink to previous/next arrow buttons. This is legible as an affordance, but in a calendar panel it can read as two extra pills. The period-picker arrows (for example `month-picker.tsx:103-109`) instead use raw `surface-action` buttons with hover-only fill and no border/shadow at rest. Candidate: align calendar arrow idle chrome to the quieter period-picker treatment; retain hit area and focus/hover paint. Keep calendar day/selected/range paint, which communicates selection.

**P2 — disclosure controls should stay text-first.** AccordionTrigger is custom Radix button markup with no base border/background (`accordion.tsx:31-48`); theme adds a well only on hover/open at `design-modes.css:917-920`. That is already an embedded disclosure presentation. Keep open/hover semantic feedback; do not run it through Button variants. Collapsible trigger is caller-owned and likewise should be styled contextually, not globally.

**P2 — field add-ons and selected values are not generic buttons.** Shared field frames at `design-modes.css:972-1024` intentionally own one joined field surface; inputs clear their inner chrome, while add-ons have a subtle tint and `field-action` reserves a hit cell. Tags chips (`1031-1036`), selected controls (`1106-1127`), menu checked/highlighted items (`755-762`), and calendar selected days are meaningful state/surface paint. Avoid a blanket `button, select { background: transparent; border:0 }` reset: it would erase standalone actions, field affordance, checked/selected state, and danger/focus/disabled distinctions.

### Recommended implementation boundary for root

Prefer semantic context hooks already present (`data-slot="block-toolbar"`, `[data-ui="field-frame"]`, `[data-ui="accordion-trigger"]`, `[data-ui="overlay-panel"]`) and add a small embedded-control slot where no component-level hook exists. Scope all appearance adaptation to the intended non-Basic design boundary; preserve the current independent local scope behavior and all 21 approved definitions. Do not mutate `--control-radius`, `--field-radius`, or global themes to solve embedded controls. Keep `outline` as a standalone/secondary action variant; let context override only embedded chrome. Paint selected/pressed state by the owning component's state hook. Keep visible keyboard focus outlines, native keyboard semantics, disabled pointer/opacity, accessible labels, and destructive/danger text.

## Coverage and handoff

- Inventory: **53/53 IDs** reviewed, comprising Actions 8, Inputs 14, Selection 13, Date & time 7, Overlays 11. (Counts are family counts from the filtered inventory; `button-group` and `pin-input` were included even though prior R15 excluded them, and `drawer` was added.)
- Source-level concrete candidates: 3 prioritized groups above: (1) generic `aria-pressed` paint cascade, (2) embedded native-select in BlockEditor toolbar, (3) inline outline actions in BlockEditor toolbar. Secondary candidates: calendar nav arrows; context-specific option rows/utility actions. All remaining IDs have current behavior and keep/flatten boundaries stated above; no filename-only PASS classification is used.
- Source hooks relevant to control chrome are centralized at `design-modes.css:372-405, 435-454, 745-763, 912-928, 935-1046, 1106-1135`. Basic caveat: 372-388 are global to `[data-design]` and therefore need a Basic-safe contract if changed; the non-Basic scoped rule at 967 cannot be assumed to repair Basic. The explicit `@scope` at 935 is limited to non-Basic design trees and should remain so.
- No runtime appearance/state result is claimed. Focus, disabled, selected, danger, native keyboard interaction, and browser cascade must be reviewed by root if implementing the candidates. Root owns implementation, browser/build/release, and PRISM regression evidence.
